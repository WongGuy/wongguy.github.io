# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A lightweight website designed to aggregate mechanical reference materials into a single unified source. Designed to have simple mechanical calculators, tables, charts, etc.

## Structure

Static site, no build step, no framework, no dependencies — plain HTML/CSS/JS loaded directly by the browser.

- `index.html` — a bare redirect (meta refresh) to `screw-selector.html`, kept only so GitHub Pages has a root document at `/`. Don't put real markup here.
- `screw-selector.html`, `nut-selector.html`, `washer-selector.html`, `nasa-tightening-torque.html`, `bolt-size-estimation.html`, `torque-tension-diagram.html` — one page per reference tool. Each has its own `<section class="chart-card">` and an empty `<div class="site-nav"></div>` that `tab-nav.js` fills with the shared two-level nav.
- `style.css` — all styling. Colors as CSS custom properties on `:root`, plus a `:root[data-theme="dark"]` block overriding the same properties for dark mode.
- `theme.js` — shared, page-agnostic dark-mode toggle. Reads/writes `localStorage` and sets `data-theme` on `<html>`; has no knowledge of any page's actual colors. Include it in `<head>`, before the stylesheet link, so the theme is applied before first paint. Any page also needs a `#theme-toggle` checkbox (see the `.theme-switch` markup in `screw-selector.html`) for the toggle to attach to.
- `site-nav-data.js` — the site's navigation structure: a list of top-level categories, each with the pages it contains. This is the only file to edit when adding, renaming, or recategorizing a page in the nav.
- `tab-nav.js` — shared, page-agnostic navigation renderer. Builds both nav bars into each page's `<div class="site-nav"></div>` from `site-nav-data.js`. The upper bar (`.category-nav`) holds the top-level categories as buttons — clicking one only swaps which tabs the lower bar shows, it never navigates. The lower bar (`.tab-nav`) holds that category's pages as links, and is the only part that navigates. On load the selected category is whichever one contains the current page. Pages just need the empty `<div class="site-nav"></div>` plus the `site-nav-data.js` and `tab-nav.js` includes — no hardcoded tab markup.
- `footer.js` — shared, page-agnostic footer content. Populates every page's `<footer>` on load with the common links (source data tables, attribution). Each page just needs an empty `<footer></footer>` and the script include.
- `flowchart.js` — shared, page-agnostic decision-tree flowchart renderer. `renderFlowchart(container, data, options)` takes a plain JSON tree (see the doc comment at the top of the file for the Node/Edge shape) and builds it as real DOM boxes with CSS-drawn connector lines, so it reflows and wraps on resize instead of breaking a fixed-width layout. Each page that shows a flowchart gets its own `tools/<tool>/<tool>-flowchart-data.js` holding just the JSON tree (plus any page-specific wiring, e.g. a detail toggle) and an empty `<div id="flowchart" class="flowchart"></div>` — see `tools/nut/nut-flowchart-data.js` (uses `options.activeTags` to toggle fine-pitch variants) and `tools/washer/washer-flowchart-data.js` (no toggle) for two different shapes of tree reusing the same renderer.
- `plot.js` — shared, page-agnostic line-plot renderer, the plotting counterpart to `flowchart.js`. `renderLinePlot(container, options)` takes a list of series (each a label, a color, and `{x, y}` points) and draws real SVG axes, gridlines, lines, markers, a legend, and a hover tooltip, re-measuring the container and redrawing on resize so the plot reflows instead of scaling. It knows nothing about what's plotted — axis titles, tick formatting, and tooltip text all come in as options. Passing the optional `legendItems` (each with an `onToggle`) turns the legend into the plot's series control: the rows are drawn as given rather than derived from what's on the plot, so a series switched off keeps a row to switch back on, and the legend survives an empty plot. Series colors are the `--series-N` custom properties in `style.css`, so lines follow the theme.
- `tools/<tool>/` — each reference tool's own data file and rendering logic (e.g. `tools/nasa-torque/nasa-torque-data.js` + `tools/nasa-torque/nasa-torque-app.js`, `tools/screw/screw-data.js` + `tools/screw/screw-app.js`). The tool's page itself stays at the repo root — only the per-tool JS lives in subfolders — so GitHub Pages URLs don't move. Shared, page-agnostic files (`theme.js`, `tab-nav.js`, `footer.js`, `flowchart.js`, `plot.js`, `site-nav-data.js`, `style.css`) stay at root since every page includes them.
  - `tools/nasa-torque/nasa-torque-data.js` — reference data for the NASA tightening torque plot: `torqueMaterials` (the five materials, ordered by ultimate shear strength) and `torqueData` (one entry per fastener size, each holding per-material rows of thread engagement, pullout load, assembly torque, and 100 % torque). Generated — see `scripts/generate_nasa_torque_data.py`. Values here are plain metric numbers rather than display strings, because `nasa-torque-app.js` does arithmetic on them.
  - `tools/nasa-torque/nasa-torque-app.js` — DOM logic for `nasa-tightening-torque.html`: the size slider (same construction as the other selectors), the plot itself via `renderLinePlot`, and the assembly/100 % torque toggle. The materials are switched on and off from the plot's own legend — the page passes `legendItems` covering every material, not just the plotted ones — rather than from a separate checkbox block. Size, torque column, and material selection all persist in `localStorage`.
  - `tools/bolt/bolt-data.js` — ISO metric bolt reference data, shared by every page under Bolting Information rather than owned by one tool: `bolt-size-estimation.html` reads the loads, `torque-tension-diagram.html` reads the thread geometry and the per-class Rp0,2. `tools/bolt/` therefore holds data only — no app file — and anything specific to one page's method belongs in that page's own tool folder. Two halves. Generated (see `scripts/generate_bolt_data.py`): `boltSeries`, `boltLoadTypes`, `boltGrades` (each with a `properties` map of Rm / Sp on the nominal basis and Rp0,2 on the minimum basis, from ISO 898-1 Table 3 — class 8.8's Rp0,2,min splits by diameter like its Sp,nom), `boltGradeProperties`, `boltThreads` (one flat array of both coarse and fine threads, sorted by diameter then pitch, each tagged with its `series`, carrying the thread geometry — `pitch`, `d2` from ISO 724, `stressArea`, and `d0 = sqrt(4 As / pi)` — and proof and minimum ultimate tensile loads per property class) and `boltNotes`. Hand-maintained: `boltLoadCases` and `boltTighteningMethods`, which aren't ISO 898-1 data but the bolt size estimation method's own step counts and load condition schematics. Values are plain numbers because the apps compare, step through, and do arithmetic on them.
  - `tools/bolt-strength/bolt-strength-app.js` — DOM logic for `bolt-size-estimation.html`: the force-per-bolt input, the load condition and tightening method pickers, the load table, and the property class column toggles. The table bolds the smallest thread that carries the entered force in each class, steps down by the load condition's plus the tightening method's step count to highlight the estimate, and trims the rows to one either side of that band. Stepping walks only the rows a class is tabulated at, so classes that stop early (9.8 above M16) step through their own sizes; a class that can't see the estimate through is marked on its column header: if nothing in it carries the load nothing in the column is marked either, but if a bare minimum exists and only the step-down runs off the bottom, that yellow minimum cell stays marked and just the green recommendation is dropped. Force, load condition, tightening method, and column selection all persist in `localStorage`. Which load type and thread series are shown come from their lists in the data file, so adding a fine-thread or tensile-load toggle is wiring a control to those sets rather than changing the table build.
  - `tools/torque-tension/torque-tension-data.js` — the assumptions behind the torque-tension diagram, and nothing else: the friction range swept to draw the curve, the yield utilization ν, and the head bearing diameter as a multiple of d. None of it comes from a standard — the standards data the page uses is all in `tools/bolt/bolt-data.js` — so it's kept here where it can be read and changed without touching the plot code. The app renders the page's assumptions list from these values too, so the numbers quoted on the page can't drift from the numbers plotted.
  - `tools/torque-tension/torque-tension-app.js` — DOM logic for `torque-tension-diagram.html`: the size slider (same construction as the other selectors), the thread parameter readout pinned under it, and the plot via `renderLinePlot`. Draws one curve per property class that ISO 898-1 gives an Rp0,2 for (8.8 and up), each a parametric sweep of the friction coefficient through the two formulas printed at the top of the page — preload on Y, tightening torque on X, so the arc lands in the first quadrant. Classes are switched from the plot's own legend, as on the NASA torque page. Coarse pitches only, and like the estimation table it blocks the ISO 262 second-choice diameters (M3.5, M14, M18, M22, …) from the slider — `SECOND_CHOICE_DIAMETERS` in the app — so it steps through the R10 preferred series. Size and class selection persist in `localStorage`.
  - `tools/screw/screw-data.js` — reference data tables for the screw selector (currently `screwData`, the ISO metric thread values, plus `screwFields` describing how to label/order them for display). This is the file to edit when adding or correcting screw reference values.
  - `tools/screw/screw-app.js` — DOM logic that reads `screw-data.js` and renders the screw selector's interactive controls (slider + spec panel). Wrapped in an IIFE, queries elements by ID, no globals besides what `screw-data.js` exposes.
- `assets/images/<tool>/` — static images for that tool's page (e.g. `assets/images/screw/thread-diagram.svg`). `nut/` and `washer/` exist as empty placeholders until those selectors have diagrams.
- `assets/standards/NASA/Torque/` — source-of-truth NASA torque data: `NASA_TM-2017-219475_Metric_Torque_Tables.xlsx` (one worksheet per material/size pair, transcribed from the report's metric tables) alongside the report PDFs. `scripts/generate_nasa_torque_data.py` rebuilds `tools/nasa-torque/nasa-torque-data.js` from the workbook, converting the US customary source values to metric on the way (in -> mm, lb -> N, lb-in -> N*m); it reads the xlsx with the standard library only, so the generators stay dependency-free.
- `assets/standards/ISO/screw/ISO Standards - ISO 898-1.xlsx` and `ISO Standards - ISO 724.xlsx` — the two source-of-truth workbooks behind `tools/bolt/bolt-data.js`. ISO 898-1:2013 carries Table 3 (mechanical properties per property class) plus one worksheet per (load type, thread series) pair (Tables 4-7 — ultimate tensile and proof loads, coarse and fine pitch); ISO 724:2023 carries Table 1 (basic dimensions) on a single worksheet, and supplies the pitch diameter d2, which ISO 898-1 doesn't tabulate and which can't be recovered from the stress area. `scripts/generate_bolt_data.py` rebuilds the generated blocks from both; like the NASA generator it reads the xlsx files with the standard library only. The values are already metric, so nothing is converted. The generator cross-checks the two workbooks against each other — ISO 724's (d2 + d3) / 2 must reproduce the d0 recovered from ISO 898-1's As — and stops if they disagree by more than the rounding of As.
- `assets/standards/ISO/<tool>/` — source-of-truth ISO standard CSVs for that tool (e.g. `assets/standards/ISO/screw/ISO Standards - ISO 262.csv`), checked in alongside a generator script (see `scripts/generate_screw_data.py`) that rebuilds the tool's `tools/<tool>/<tool>-data.js` from them. `nut/` and `washer/` exist as empty placeholders until those standards are sourced.

Each reference tool follows the same pattern: a data file (e.g. `tools/screw/screw-data.js`) describing the values, plus rendering logic (e.g. `tools/screw/screw-app.js`) that builds the table/panel from it. When adding a new reference tool, give it its own root-level `<tool>-selector.html`, a `tools/<tool>/` folder holding `<tool>-data.js` and `<tool>-app.js`, `assets/images/<tool>/`, and `assets/standards/ISO/<tool>/`, following this same data/render split rather than hardcoding values into HTML. Add the page to `site-nav-data.js` so it shows up in the nav.

When adding a new page, give it its own stylesheet (or its own `:root` / `:root[data-theme="dark"]` blocks) so it can define a completely independent light/dark palette — `theme.js` is shared and reusable as-is, but colors are never shared, they're per-page CSS custom properties.

## Working in this repo

- Assume this project is hosted on github pages, with the site being deployed from main. Make sure that the site can always be easily ported to standalone if needed.
- Avoid fillets on page elements when possible in favor of sharp rectangular elements.
